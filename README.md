# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks` -- создание задачи (опционально с генерацией цепочки)
- `GET /api/v1/tasks` -- список всех задач
- `GET /api/v1/tasks/{id}` -- получить задачу по ID
- `PUT /api/v1/tasks/{id}` -- обновить **одну** задачу
- `DELETE /api/v1/tasks/{id}` -- удалить задачу

Маршруты для работы с цепочками задач:

- `POST /api/v1/tasks/{id}/chain` -- превратить задачу в мастер и сгенерировать цепочку
- `GET /api/v1/tasks/{id}/chain` -- получить всю цепочку (мастер + дочерние)
- `PUT /api/v1/tasks/{id}/chain` -- обновить **только заголовок и описание** мастер-задачи и распространить их на дочерние задачи со статусом `new`
- `PUT /api/v1/tasks/{id}/propagate` -- догенерировать новые задачи в цепочке (пропагация) по существующему расписанию

## Генерация по расписанию

Сервис позволяет создавать **мастер-задачи** с автоматической генерацией цепочки дочерних задач по заданному расписанию.  
Расписание задаётся полем `chain_generation.schedule` при создании задачи или при вызове `POST /api/v1/tasks/{id}/chain`.

### Типы расписаний

Поля расписания **взаимоисключающие** -- в одном запросе можно указать только один тип.

| Поле | Тип | Описание |
|------|-----|-----------|
| `sparse_dates` | `array` строк `date-time` | Создать задачи только в указанные даты (без проверки рабочих дней, без окон генерации) |
| `every_nth_day` | натуральное число | Создать задачу каждый N-й день (учитываются только рабочие дни, фильтрация по окну `start`/`end`) |
| `every_nth_monthday` | целое число ([1,31]) | Создать задачу в N-й день каждого месяца (рабочие дни, окно) |
| `every_even_day` | логический (`true`/`false`) | `true` -- чётные дни месяца, `false` -- нечётные (рабочие дни, окно) |

**Окно генерации** задаётся полями `start` и `end` (внутри `chain_generation`).  
- Для `sparse_dates` эти поля игнорируются
- Для остальных типов задают диапазон дат, в котором будут создаваться задачи (включительно `start`, исключая `end`)
- Если `start` не указан -- берётся текущий момент времени
- Если `end` не указан -- `start + 3 месяца`

При указании N-го числа месяца больше, чем есть в месяце, будет использоваться последняя доступная дата месяца.
Т.е. 29 фев. станет 28 (кроме високосных), 30, 31 станут 28; 31 апр. станет 30 (аналогично для других 30-дневных месяцев).

### Примеры

#### 1. Расписание по конкретным датам (без окон)

```json
{
  "title": "Релиз документации",
  "status": "new",
  "chain_generation": {
    "schedule": {
      "sparse_dates": [
        "2026-05-01T10:00:00Z",
        "2026-06-01T10:00:00Z",
        "2026-07-01T10:00:00Z"
      ]
    }
  }
}
```

Создаст мастер-задачу и ровно три дочерних -- на указанные даты.

#### 2. Каждый 3-й день в течение двух месяцев (только рабочие)

```json
{
  "title": "Проверка очереди",
  "start_at": "2026-04-01T08:00:00Z",
  "deadline": "2026-04-01T09:00:00Z",
  "chain_generation": {
    "schedule": { "every_nth_day": 3 },
    "start": "2026-04-02T00:00:00Z",
    "end": "2026-06-01T00:00:00Z"
  }
}
```

#### 3. 15-е число каждого месяца (с мая по декабрь)

```json
{
  "title": "Платёж по ипотеке",
  "chain_generation": {
    "schedule": { "every_nth_monthday": 15 },
    "start": "2026-05-01T00:00:00Z",
    "end": "2027-01-01T00:00:00Z"
  }
}
```

#### 4. Чётные дни (только рабочие)

```json
{
  "title": "Ежедневный отчёт (чётные дни)",
  "chain_generation": {
    "schedule": { "every_even_day": true },
    "start": "2026-04-01T00:00:00Z",
    "end": "2026-05-01T00:00:00Z"
  }
}
```

### Поведение при создании цепочки

- Мастер-задача создаётся и сохраняется в БД с полем `schedule`
- Дочерние задачи генерируются и вставляются массово
- В ответе на `POST /tasks` возвращается **только** мастер-задача (дочерние не выводятся)
- При вызове `POST /tasks/{id}/chain` существующая задача превращается в мастер, 
  и возвращается массив задач, содержащий мастера и все сгенерированные дочерние.
  Если задача является мастером и имеет зависимые задачи, то возникнет ошибка
- При вызове `PUT /tasks/{id}/propagate` продляется цепочка по расписанию. 
  Датой начала берется последняя дата из цепочки и указанного времени 

### Обновление мастер-задачи с распространением (`PUT /tasks/{id}/chain`)

Этот эндпоинт предназначен **только для обновления заголовка и описания мастер-задачи** 
с автоматическим применением этих изменений ко всем дочерним задачам со статусом `new`. 

- Другие поля (`status`, `start_at`, `deadline`, `schedule`) игнорируются
- `make_standalone` не поддерживается
- Изменения `start_at`/`deadline` не происходят -- для изменения времени используйте обычный `PUT /tasks/{id}` (но это разорвёт связь с цепочкой)
- В ответе возвращается вся обновлённая цепочка (мастер + все дочерние задачи)

### Пропагация цепочки (добавление новых задач) -- `PUT /tasks/{id}/propagate`

Если цепочка уже существует, а нужно добавить новые задачи после последней имеющейся 
(например, приблизился конец окна), используется **пропагация**.

- Для `sparse_dates`: генерирует все даты из списка, которых ещё нет в цепочке (параметры `start`/`end` игнорируются)
- Для остальных типов:  
  Находит самую позднюю дату `start_at` среди дочерних задач (исключая мастера) и 
  генерирует новые задачи от этой даты (или от указанного в запросе `start`) до `end` (или до `start+3 месяцев`).

### Обновление задачи без распространения (`PUT /tasks/{id}`)

Обычный `PUT /tasks/{id}` обновляет только саму задачу и **не затрагивает** дочерние задачи, даже если задача является мастером.  
Этот эндпоинт предназначен для точечных изменений (например, смена статуса, времени), когда не нужно влиять на цепочку.  
- При изменении `start_at` или `deadline` связь с цепочкой разрывается (`master_task_id = null`).  
- При установке `make_standalone: true` задача также отсоединяется от цепочки.

### Валидация

- Заголовок (`title`) обязателен, не может быть пустым
- Если указан `deadline`, то `start_at` тоже должен быть задан, и `deadline` должен быть позже `start_at`
- Поля расписания взаимоисключающие (нельзя указать одновременно `every_nth_day` и `sparse_dates`)
- Для `sparse_dates` даты должны быть уникальны
- Для `every_nth_monthday` значение должно быть от 1 до 31 включительно

### Обратная совместимость

Обновленное API полностью обратно совместимо -- все новые поля опциональны, валидируются только при предоставлении.
Возвращаемые объекты расширены (предполагается, что клиент игнорирует лишние данные).
Старые эндпоинты при использовании нового функционала возвращают не списки, а также по одной задаче.
Структура БД и доменных моделей также позволяет использовать их в других модулях, нет ломающих изменений.

## Принятые решения

Реализация фичи выполнена с оглядкой на обратную совместимость -- 
по условию не известно кто потребитель, разумно предполагать, что клиент не может обновить запросы.
Потенциально ломающие изменения: возвращаемые объекты обновлены, если клиент строго проверяет формат ответа
это сломает совместимость.
Возможное (не) решение: требовать указывать заголовок, который есть только у новых клиентов, тогда формат ответа будет новый.
Однако это имеет мало смысла с практической точки зрения, если не создавать систему версирования API по заголовкам (как у Stripe).

Удаление задач оставлено позадачно осознанно, это обезопашивает от сценария удаления целой цепочки важных задач.

Аналогично с пересозданием задачи, перезапись цепочки может затереть важные сведения незаметно.

При изменении времени задачи она намеренно отделяется от цепочки, она начинает выпадать из расписания.
При создании цепочки из задачи задача становится мастер-задачей, чтобы не создавать цепочки, зависимые от цепочек.

Создание задач в указанные даты сохраняет мастер задачу, как и остальные варианты.
Это сделано для унификации поведения.

Созданная мастер-задача может выпадать из расписания -- это сделано из соображений,
что сценарий использования: "создай задачу в указанное время и повтори вот по этому шаблону".

Обновление статуса на мастер-задаче не затрагивает остальные задачи, 
зависимые задачи повторяются по расписанию, но в остальном слабо зависят от мастера.

Обновление заголовка и описания на мастер-задаче влечёт обновление у зависимых только по явному указанию,
потому что мастер является шаблоном.

## Возможные улучшения

Усложнение проверки на рабочий день. Учет праздников, часовых поясов. Также добавление проверки с учетом пользователей.

Фиксация задач от изменения.

Добавление фич для автоматического мониторинга статуса (при истечении задачи).

Добавление новых сценариев генерации, например, последняя среда месяца.

Усложнение правил сдвига дат при генерации, например, сдвиг не только назад, но и вперед.

Фильтрация задач при получении, по различным полям.
